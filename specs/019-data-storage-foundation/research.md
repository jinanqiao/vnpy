# 研究结论：数据存储底座改造

## 决策：大规模行情数据继续使用 parquet

**理由**：当前项目已经用 parquet 存储 OHLCV、股票池、基准、行业和 AKShare 数据。Parquet 是列式格式，压缩率好，适合 Polars 和 DuckDB 这类分析工具。当前本地数据约 2.4G，用户已预留 100G 空间，因此 parquet 仍是最简单、稳定、可扩展的主存储。

**考虑过的替代方案**：

- 全部进入 PostgreSQL：拒绝。日线、分钟线等行情数据更适合列式扫描，放入行式数据库会增加存储重复和查询成本。
- 全部进入 SQLite：拒绝。SQLite 适合小型关系数据，不适合承载大规模行情明细。
- 立即上 ClickHouse：推迟。当前数据规模和单机工作流还不需要服务端列式数据库。

## 决策：增加 DuckDB 风格的分析查询层

**理由**：用户希望“像数据库一样查”，但又不想过早迁移全部数据。DuckDB 可以直接查询 parquet，并能在本地提供 SQL 视图。这能改善研究体验，同时保留 parquet 的可移植性和低运维成本。

**考虑过的替代方案**：

- 只用 Polars 脚本查 parquet：可行，但临时 join、审计和交互式查询不如 SQL 方便。
- 导入服务端数据库：当前阶段运维成本过高。

## 决策：SQLite 先做元数据和运行状态，PostgreSQL 作为升级路径

**理由**：数据版本、质量结果、数据源覆盖、信号运行、风控事件等记录体量小、关系清晰、需要审计。单机阶段 SQLite 足够。等出现多进程写入、远程看板、多人协作或服务化部署时，再升级 PostgreSQL。

**考虑过的替代方案**：

- 只用 JSON 存元数据：初期简单，但后续查询 run lineage、质量历史和版本关系会很别扭。
- 立即上 PostgreSQL：能力更强，但当前本地单用户阶段不是必要复杂度。

## 决策：QMT 做交易相关主源，AKShare 做研究补充和交叉校验

**理由**：QMT/XtQuant 已经接入项目，并且适合行情、实时状态和执行相关场景。AKShare 对财务报表、流通股本、换手率和公开网页类数据很有价值，但接口稳定性和字段变化风险更高，不适合作为实盘执行唯一依据。

**考虑过的替代方案**：

- 只依赖 QMT：拒绝。当前 QMT 财务 probe 返回 available-but-empty，且部分 PIT 补充数据需要其他来源。
- 只依赖 AKShare：拒绝。实盘行情和交易执行应以 QMT 为准。

## 决策：定义多种数据就绪模式

**理由**：研究、回测、模拟交易和实盘对数据缺陷的容忍度不同。过期数据可能还适合历史研究，但不适合实盘生成订单候选。

**考虑过的替代方案**：

- 单一 pass/fail 状态：拒绝。它无法表达“研究可用但实盘不可用”的常见状态。

## 决策：显式建立 PIT 目标表

**理由**：当前项目已经记录了历史指数成分、历史 ST、涨跌停、停复牌、公司行动和行业归属等缺口。把 PIT 表显式列为目标，有助于从学习/研究级数据逐步升级到可实盘验证的数据。

**考虑过的替代方案**：

- 继续只在报告里写局限性：短期可用，但不适合实盘级回测。

## 决策：迁移必须增量进行

**理由**：现有本地数据已经有价值，不能为了新目录结构直接删除或覆盖。第一阶段应先做映射、manifest 和查询层，再逐步物理迁移。

**考虑过的替代方案**：

- 立即物理搬迁所有文件：拒绝。合同和质量门禁没稳定前风险过高。
